1. 项目概述

核心 proxy_ob 是一个用 Go 语言编写的加密隧道代理。它通过 ChaCha20-Poly1305 AEAD 加密，将本地网络流量安全地转发到远端服务器，支持 SOCKS5、HTTP/HTTPS 代理协议、TCP 端口转发和反向隧道。

整个项目编译为单个二进制文件，通过子命令切换四种运行模式。唯一的外部依赖是 golang.org/x/crypto（用于 ChaCha20-Poly1305 实现），编译后体积约 3MB。

属性值
语言Go 1.25
加密ChaCha20-Poly1305 AEAD（每帧随机 nonce + 16 字节认证标签）
认证HMAC-SHA256 预共享密钥令牌（常量时间比较）
代理协议SOCKS5 TCP CONNECT (RFC 1928) + HTTP CONNECT + 普通 HTTP 代理
运行模式client / server / forward / reverse
外部依赖仅 golang.org/x/crypto
平台Linux amd64 / Windows amd64 / macOS arm64+amd64
测试覆盖24 个单元测试（crypto / tunnel / socks5 / http_proxy / reverse spec）

2. 四种运行模式

2.1 client — SOCKS5 / HTTP 代理客户端

在本地启动代理监听端口（默认 127.0.0.1:1080），自动检测连接是 SOCKS5 还是 HTTP 代理协议。每个用户连接都会创建一条独立的加密隧道到远端 server，目标地址通过第一帧发送。

本地应用                     Client (:1080)                 Server (:8388)           目标
│                               │                              │                      │
│  SOCKS5 / HTTP CONNECT        │                              │                      │
│ ─────────────────────────────►│                              │                      │
│                               │  HMAC 握手 + 加密目标地址帧    │                      │
│                               │ ═══════════════════════════► │                      │
│                               │                              │  net.Dial(target)    │
│                               │                              │ ────────────────────►│
│  ←━━━━━━━━━ 双向加密中继 ═══════════════════════════════════════════════━━━━━━━━━━━→ │

# 用法
./proxy_ob client -s server-ip:8388 -k "secret-key"
curl --socks5 127.0.0.1:1080 http://httpbin.org/ip
curl -x http://127.0.0.1:1080 https://httpbin.org/ip

2.2 server — 隧道服务端

在远端服务器启动隧道监听（默认 :8388）。接收客户端的隧道连接，验证 HMAC 握手，读取第一帧的目标地址，连接目标后双向中继。server 端协议无关 — 不区分流量来自 SOCKS5 还是 HTTP 代理，只看目标地址帧。

连接数上限 1024（通过 semaphore 实现），每个连接 10 秒 dial 超时。

2.3 forward — 本地端口转发

类似 SSH -L。在本地监听 TCP 端口，将所有流量通过隧道转发到 server 端的预配置固定目标。跳过 SOCKS5/HTTP 协议解析，目标地址在启动时通过 -t 参数指定。

本地应用             Forward (:3306)              Server (:8388)          内网目标
│                       │                            │                      │
│  原始 TCP 连接         │                            │                      │
│ ─────────────────────►│                            │                      │
│                       │  HMAC 握手 + 固定目标帧     │                      │
│                       │ ═════════════════════════► │                      │
│                       │                            │  net.Dial(target)    │
│                       │                            │ ────────────────────►│
│  ←━━━━━━ 双向加密中继 ═════════════════════════════════════════════━━━━━━→ │

./proxy_ob forward -l :3306 -t 10.0.0.5:3306 -s server-ip:8388 -k "key"
mysql -h 127.0.0.1 -P 3306  # 直连本地端口，实际访问 server 内网

2.4 reverse — 反向端口转发 / 反向通用代理

类似 SSH -R。客户端（在 NAT 后方）主动连接服务器建立控制连接，服务器开放端口供外部访问。当外部用户连入时，服务器通过控制连接通知客户端，客户端发起数据连接到服务器，双向中继。

支持两种子模式：

  • 固定目标：-r 3306:10.0.0.5:3306 — 每个连接映射到同一目标
  • 通用代理：-r 1080 — 服务器暴露 SOCKS5/HTTP 代理，目标由用户动态指定

绑定地址约定：1080 = 仅本机 127.0.0.1:1080；:1080 = 全接口 0.0.0.0:1080

用户                    Server (:8388 + :1080)              Client (NAT 后方)
│                          │                                   │
│                          │  ←━━ 控制连接（持久）━━━━━━━━━━━━━ │  (1) 注册
│                          │                                   │
│  SOCKS5 / TCP 连接        │                                   │
│ ────────────────────────►│                                   │
│                          │  ── 连接请求 (session ID) ──────►  │  (2) 通知
│                          │                                   │
│                          │  ◄━━ 数据连接 (session ID) ━━━━━━ │  (3) 建立
│                          │                                   │
│                          │                      连接本地目标 ──►  10.0.0.5:3306
│  ←━━━━━━━━━━ 双向加密中继 ═════════════════════════════════════ │

# 固定目标反向转发
./proxy_ob reverse -r 3306:10.0.0.5:3306 -s server-ip:8388 -k "key"

# 反向通用代理（SOCKS5/HTTP）
./proxy_ob reverse -r 1080 -s server-ip:8388 -k "key"
curl --socks5 server-ip:1080 http://10.0.0.5:8080

3. 加密体系

ChaCha20-Poly1305 AEAD

每次加密使用 12 字节随机 nonce，附加 16 字节 Poly1305 认证标签。AEAD 模式同时提供加密和完整性校验 — 如果密文被篡改，解密会失败。

选择 ChaCha20 而非 AES-GCM 的原因：在没有 AES 硬件加速的平台上（如部分 ARM 设备）性能更优，且不存在 nonce 误用的灾难性后果。

密钥派生

DeriveKey(key string) [32]byte 支持两种输入：

  • Hex 密钥（64 个十六进制字符）：直接解码为 32 字节密钥
  • 密码短语（任意长度）：通过 SHA-256 哈希派生为 32 字节
// internal/crypto.go
func DeriveKey(key string) [32]byte {
    if len(key) == 64 {
        if b, err := hex.DecodeString(key); err == nil && len(b) == 32 {
            var out [32]byte
            copy(out[:], b)
            return out
        }
    }
    return sha256.Sum256([]byte(key))
}

4. 隧道帧协议

所有隧道数据都以帧为单位传输。每帧包含一个可选的目标地址和任意长度的数据载荷，整体加密后通过 TCP 传输。

Wire 格式

[2 字节长度 (big-endian)] [加密载荷]

加密载荷 = ChaCha20-Poly1305(明文)
明文结构 = [1 字节 Atyp] [地址数据] [2 字节端口] [数据载荷]

Atyp 地址类型

值含义地址字段用途
0x01IPv44 字节正常代理 / 中继数据帧
0x03域名1 字节长度 + 域名正常代理 / 中继数据帧
0x04IPv616 字节正常代理 / 中继数据帧
0x00控制帧无地址反向隧道注册
0x02控制帧无地址固定目标连接请求（server→client）
0x05控制帧无地址反向数据连接初始化（client→server）

帧上限

Wire 帧上限约 65KB（uint16 长度前缀）。中继时使用 32KB 读取缓冲区，确保每帧在限制内。

中继帧约定

双向中继过程中的数据帧使用 Atyp=0x01, Addr=4个零字节 作为哑值，实际载荷在 Data 字段中。地址信息仅在第一帧（目标地址帧）中有意义。

5. 握手认证

隧道连接建立后、帧传输之前，双方进行 HMAC 握手认证。这是一个无状态、确定性的认证方案 — 双方从相同密钥派生出相同的令牌。

令牌派生

token = HMAC-SHA256(key, key)  →  32 字节

双方各自计算 HandshakeToken(key)，结果相同。令牌不随连接变化，不需要维护会话状态。

握手流程

Client → Server:  [0x01 版本号] [32 字节 HMAC 令牌]     共 33 字节
Server → Client:  [0x01 版本号] [0x00=成功 / 0x01=失败]    共 2 字节

安全特性

  • 常量时间比较：subtle.ConstantTimeCompare 防止时序攻击
  • 无明文密码传输：令牌是 HMAC 派生值，不是原始密钥
  • 前向安全依赖：每帧使用独立随机 nonce，即使 nonce 重复也不会泄露密钥

6. 协议自动检测

client 模式在同一端口同时支持 SOCKS5 和 HTTP 代理。无需配置切换，通过首字节自动判断协议。

检测原理

协议首字节原因
SOCKS50x05SOCKS5 版本号字段固定为 5
HTTP 代理ASCII 字母HTTP 方法首字母（C=CONNECT, G=GET, P=POST 等）

实现：bufferedConn 包装器

使用 bufio.Reader.Peek(1) 无消费读取首字节。判断后，SOCKS5 路径需要继续读取完整握手数据，因此用 bufferedConn 包装连接，让 bufio.Reader 中已缓冲的数据在后续 Read() 中被正确读取。

// cmd/client.go
type bufferedConn struct {
    r  *bufio.Reader
    net.Conn          // 嵌入 net.Conn 提供 Write/Close/RemoteAddr 等
}

func (bc *bufferedConn) Read(b []byte) (int, error) {
    return bc.r.Read(b)  // Read 委托给 bufio.Reader
}

func handleConnection(conn net.Conn, cfg *internal.Config, key [32]byte) {
    br := bufio.NewReader(conn)
    peek, _ := br.Peek(1)

    if peek[0] == 0x05 {
        handleSOCKS5(&bufferedConn{r: br, Conn: conn}, cfg, key)
    } else {
        handleHTTPProxy(br, conn, cfg, key)
    }
}

7. 双向中继机制

relay() 是整个项目的核心函数，被 client、forward、reverse 三种模式共用。它在两条连接之间双向搬运数据，一端是原始 TCP（用户 / 本地目标），另一端是加密隧道。

并发模型

         ┌──── goroutine 1 ────┐
         │                      │
         │  localConn.Read()    │
         │       ↓              │
         │  Frame{Data: buf}    │
         │       ↓              │
         │  WriteFrame(tunnel)  │  ← 加密写入隧道
         │                      │
         └──────────────────────┘

         ┌──── goroutine 2 ────┐
         │                      │
         │  ReadFrame(tunnel)   │  ← 解密读取隧道
         │       ↓              │
         │  localConn.Write()   │
         │                      │
         └──────────────────────┘

  closeAll() ← 任一 goroutine 出错即关闭两端

关键设计

  • sync.Once 关闭：closeAll 使用 sync.Once 确保双端连接只关闭一次
  • 32KB 缓冲：读取缓冲区 32KB，远小于 65KB 帧上限
  • 错误即终止：任一方向出错，立即关闭两端连接，不等超时
  • 哑地址帧：中继帧用 Atyp=0x01, Addr=4零字节，仅 Data 字段有实际数据

8. 反向隧道与通用代理

反向隧道是最复杂的功能，使用控制连接 + 数据连接分离的架构，无需引入连接多路复用库。

3.1 注册阶段（控制连接）

客户端连接服务器后发送注册帧：

Frame {
    Atyp: 0x00,                    // 注册标记
    Port: 1080,                    // 服务器端监听端口
    Data: "127.0.0.1\n"            // bind地址 + \n + 目标
         或 "127.0.0.1\n10.0.0.5:3306"
}

服务器解析 Data 字段：以 \n 分割，第一部分是绑定地址，第二部分是目标地址（为空表示通用代理模式）。

3.2 连接请求阶段（有用户连入时）

服务器通过控制连接发送连接请求帧：

固定目标模式 
Frame {
    Atyp: 0x02,           // 固定标记
    Data: "a1b2c3d4..."   // session ID
}
通用代理模式 
Frame {
    Atyp: 0x03,           // 目标地址类型
    Addr: "internal-db",  // 目标域名
    Port: 3306,           // 目标端口
    Data: "a1b2c3d4..."   // session ID
}

通用代理模式下，服务器端的监听器先与用户做 SOCKS5/HTTP 握手提取目标地址，然后把目标编码进连接请求帧。客户端通过 Atyp 区分两种模式：0x02 = 固定目标，0x01/0x03/0x04 = 动态目标。

3.3 数据连接阶段

客户端收到连接请求后，发起新的 TCP 连接到服务器（复用 HMAC 握手）：

Client → Server: 新 TCP 连接 + HMAC 握手
Client → Server: Frame { Atyp: 0x05, Data: sessionID }
Server: 匹配 sessionID，找到 pending 的用户连接
Server: relay(userConn, dataConn)  // 双向中继
Client: relay(localTarget, dataConn)  // 连接本地目标

3.4 并发安全

通用代理模式下，多个用户可能同时连入。每个用户连接在独立 goroutine 中处理，会并发写控制连接。通过 sync.Mutex 保护 WriteFrame 调用。

mu.Lock()
err = internal.WriteFrame(controlConn, key, frame)
mu.Unlock()

3.5 Session 管理

全局 sync.Map 存储 pending 连接：

var pendingReverseConns sync.Map  // sessionID → *pendingConn

type pendingConn struct {
    conn        net.Conn  // 用户连接（可能是 bufferedConn）
    initialData []byte    // HTTP 非 CONNECT 的重写请求头
}

initialData 用于普通 HTTP 代理请求：用户发送 GET http://host/path HTTP/1.1，服务器重写为 GET /path HTTP/1.1 并存入 initialData。数据连接建立后，服务器先发送 initialData 帧给客户端，客户端转发给本地目标，然后进入正常中继。

9. Daemon 后台模式

通过 -d 参数启用。使用 re-exec 模式：父进程去掉 -d 参数启动子进程，重定向 stdout/stderr 到日志文件，然后父进程退出。

跨平台实现

平台文件系统调用效果
Linux / macOSdaemon_unix.gosyscall.SysProcAttr{Setsid: true}创建新会话，脱离控制终端
Windowsdaemon_windows.gosyscall.SysProcAttr{CreationFlags: CREATE_NEW_PROCESS_GROUP}创建新进程组，脱离控制台

通过 Go //go:build 标签自动选择平台实现，CI 交叉编译时编译器自动处理。

PID 文件

父进程启动子进程后，将子进程 PID 写入 proxy_ob.pid，方便用户管理进程。

12. 关键设计决策

为什么每连接独立隧道？

每个用户连接创建一条新的 TCP 隧道连接到 server。这看似浪费，但带来了关键优势：无锁、无状态、无连接池管理。server 端每个连接独立处理，goroutine 间无共享状态。对于代理场景（连接通常持续几秒到几分钟），TCP 连接创建的开销可以忽略。

为什么 server 端协议无关？

Server 端不解析 SOCKS5 或 HTTP 协议 — 它只读取第一帧的目标地址，然后连接目标并中继。这意味着 client、forward、reverse 三种模式可以共用同一套 server 代码，无需任何修改。添加新的代理协议只需改 client 端。

为什么反向隧道用控制连接 + 数据连接？

而非单连接多路复用（如 yamux/smux）。原因：零依赖。控制连接仅传小帧（session ID），数据连接复用现有隧道协议（HMAC 握手 + Frame + relay）。实现复杂度约 200 行，无需引入第三方库。

为什么 HTTP 非 CONNECT 需要重写请求？

普通 HTTP 代理请求使用绝对 URI（GET http://host/path HTTP/1.1）。但目标服务器期望相对路径（GET /path HTTP/1.1）。因此在 client 端解析请求行，提取目标地址，重写为相对路径后作为 Frame.Data 通过隧道首帧发送。server 端将首帧 Data 直接写入目标连接。

为什么选择 re-exec 而非 fork 实现 daemon？

Go 不支持传统的 fork()。re-exec 模式（os.StartProcess）是 Go 中实现 daemon 的标准方法：父进程启动去掉 -d 的子进程副本，重定向 I/O 到日志文件，然后退出。子进程从头开始正常执行。通过 //go:build 标签，Unix 用 setsid 脱离终端，Windows 用 CREATE_NEW_PROCESS_GROUP 脱离控制台。
