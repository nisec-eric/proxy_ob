1. 项目概述

核心 proxy_ob 是一个用 Go 语言编写的加密隧道代理。它通过 ChaCha20-Poly1305 AEAD 加密，将本地网络流量安全地转发到远端服务器，支持 SOCKS5、HTTP/HTTPS 代理协议、TCP 端口转发和反向隧道。

整个项目编译为单个二进制文件，通过子命令切换四种运行模式。唯一的外部依赖是 golang.org/x/crypto，编译后体积约 3MB。

认证HMAC-SHA256 预共享密钥令牌（常量时间比较）

2. 四种运行模式

2.1 client — SOCKS5 / HTTP 代理客户端

在本地启动代理监听端口（默认 127.0.0.1:1080），自动检测连接是 SOCKS5 还是 HTTP 代理协议。每个用户连接创建一条独立加密隧道到远端 server，目标地址通过第一帧发送。

./proxy_ob client -s server-ip:8388 -k "secret-key"
curl --socks5 127.0.0.1:1080 http://httpbin.org/ip
curl -x http://127.0.0.1:1080 https://httpbin.org/ip

2.2 server — 隧道服务端

在远端服务器启动隧道监听（默认 :8388）。验证 HMAC 握手后，读取第一帧的目标地址，连接目标并双向中继。server 端协议无关 — 不区分 SOCKS5 还是 HTTP 代理，只看目标地址帧。连接数上限 1024，每个连接 10 秒 dial 超时。

2.3 forward — 本地端口转发

类似 SSH -L。在本地监听 TCP 端口，将所有流量通过隧道转发到 server 端的预配置固定目标。跳过 SOCKS5/HTTP 解析。

./proxy_ob forward -l :3306 -t 10.0.0.5:3306 -s server-ip:8388 -k "key"
mysql -h 127.0.0.1 -P 3306

2.4 reverse — 反向端口转发 / 反向通用代理

类似 SSH -R。客户端主动连接服务器建立控制连接，服务器开放端口供外部访问。支持固定目标（-r 端口:目标）和通用代理（-r 端口）两种子模式。

# 固定目标
./proxy_ob reverse -r 3306:10.0.0.5:3306 -s server-ip:8388 -k "key"
# 通用代理（SOCKS5/HTTP）
./proxy_ob reverse -r 1080 -s server-ip:8388 -k "key"

3. 加密体系

ChaCha20-Poly1305 AEAD

每次加密使用 12 字节随机 nonce，附加 16 字节 Poly1305 认证标签。AEAD 同时提供加密和完整性校验。选择 ChaCha20 而非 AES-GCM：无 AES 硬件加速时性能更优，且 nonce 重复不会泄露密钥。

密钥派生

  • Hex 密钥（64 字符）：直接解码为 32 字节
  • 密码短语（任意长度）：SHA-256 派生为 32 字节
func DeriveKey(key string) [32]byte {
    if len(key) == 64 {
        if b, err := hex.DecodeString(key); err == nil && len(b) == 32 {
            var out [32]byte
            copy(out[:], b)
            return out
        }
    }
    return sha256.Sum256([]byte(key))
}

4. 隧道帧协议

所有隧道数据以帧为单位传输，整体加密后通过 TCP 发送。

Wire 格式

[2 字节长度 BE] [加密载荷]

加密载荷 = ChaCha20-Poly1305( 明文 )
明文     = [1B Atyp] [地址] [2B 端口] [数据]

Atyp 地址类型

值含义地址字段用途
0x01IPv44 字节代理 / 中继数据帧
0x03域名1B 长度 + 域名代理 / 中继数据帧
0x04IPv616 字节代理 / 中继数据帧
0x00控制无反向隧道注册
0x02控制无固定目标连接请求
0x05控制无反向数据连接初始化

中继帧用 Atyp=0x01, Addr=4零字节 哑值，实际数据在 Data 字段。Wire 帧上限约 65KB。

5. 握手认证

隧道连接建立后、帧传输之前，双方进行 HMAC 握手。这是无状态、确定性方案 — 双方从相同密钥派生出相同令牌。

token = HMAC-SHA256(key, key) → 32 字节

Client → Server: [0x01] [32B 令牌]    共 33 字节
Server → Client: [0x01] [0x00=成功]    共 2 字节
  • 常量时间比较：subtle.ConstantTimeCompare 防时序攻击
  • 无明文密码：传输的是 HMAC 派生值
  • 每帧独立 nonce：即使 nonce 重复也不泄露密钥

6. 协议自动检测

client 模式在同一端口同时支持 SOCKS5 和 HTTP 代理，通过首字节自动判断。

协议首字节原因
SOCKS50x05SOCKS5 版本号固定为 5
HTTP 代理ASCII 字母HTTP 方法首字母（C/G/P）

使用 bufio.Reader.Peek(1) 无消费读取首字节，再用 bufferedConn 包装确保后续 Read 正确读取已缓冲数据。

type bufferedConn struct {
    r  *bufio.Reader
    net.Conn
}
func (bc *bufferedConn) Read(b []byte) (int, error) {
    return bc.r.Read(b)
}

7. 双向中继机制

relay() 被 client、forward、reverse 三种模式共用。在原始 TCP 和加密隧道之间双向搬运数据。

8. 反向隧道与通用代理

使用控制连接 + 数据连接分离架构，无需连接多路复用库。

注册阶段

Frame {
    Atyp: 0x00,
    Port: 1080,
    Data: "127.0.0.1\n"                 // bind + \n + 空 = 通用代理
         或 "127.0.0.1\n10.0.0.5:3306"  // bind + \n + target = 固定目标
}

连接请求阶段

固定目标（Atyp=0x02） 
Frame {
    Atyp: 0x02,
    Data: sessionID
}
通用代理（Atyp=0x01/03/04） 
Frame {
    Atyp: 0x03,
    Addr: "target",
    Port: 3306,
    Data: sessionID
}

通用代理模式下，服务器先与用户做 SOCKS5/HTTP 握手提取目标，再编码进连接请求帧。客户端通过 Atyp 区分：0x02 = 固定，0x01/03/04 = 动态。

并发安全

多用户同时连入时，sync.Mutex 保护对控制连接的 WriteFrame 调用。

Session 管理

type pendingConn struct {
    conn        net.Conn
    initialData []byte  // HTTP 非 CONNECT 重写请求头
}

使用 re-exec 模式：父进程去掉 -d 启动子进程，重定向 I/O 到日志文件，然后退出。

12. 关键设计决策

为什么每连接独立隧道？

无锁、无状态、无连接池管理。每个连接独立处理，goroutine 间无共享状态。TCP 连接创建开销在代理场景中可忽略。

为什么 server 端协议无关？

Server 只读第一帧目标地址，不解析 SOCKS5/HTTP。同一套 server 代码服务所有模式。添加新代理协议只需改 client 端。

为什么反向隧道用控制 + 数据连接？

零依赖。控制连接传小帧（session ID），数据连接复用现有隧道协议。约 200 行实现，无需 yamux/smux。

为什么 HTTP 非 CONNECT 需要重写？

代理请求用绝对 URI（GET http://host/path），目标服务器期望相对路径（GET /path）。Client 端重写后作为 Frame.Data 首帧发送。

为什么用 re-exec 而非 fork？

Go 不支持 fork()。os.StartProcess 启动去掉 -d 的子进程，重定向 I/O 后父进程退出。//go:build 标签实现跨平台脱离终端。
